1 · Process Concept

1.1 四个基本 OS 概念

概念 含义
Process 一个正在执行的程序的实例——由一个地址空间和一个或多个控制线程组成
Thread（Ch4） 一个唯一的执行上下文，完整描述程序状态——由 PC、registers、execution flags、stack 刻画
Address space（Ch9） 程序在自己的地址空间执行，与其他程序的不同（logical / virtual address，Ch9–10）
Dual mode operation 基本保护：用户程序和 OS（kernel）在不同 mode 运行；只有 OS 能访问某些资源；OS 和硬件不受用户程序破坏；用户程序彼此隔离

1.2 进程的组成

  • OS 执行各种程序，每个作为一个 process 运行；process 的执行按顺序推进（von Neumann）
  • 一个 process 包含：
部分 内容
Text section 程序代码
Current activity / state PC、processor registers
Stack 调用函数时的临时数据：函数参数、返回地址、局部变量
Data section 全局变量
Heap 运行时动态分配的内存
  • Program 是被动实体（磁盘上的可执行文件）；process 是主动实体，有一个 PC 指向下一条要取的指令，以及一组资源（含地址空间）
  • process 有生命周期：从开始执行到终止

1.3 Program 怎样变成 process

  • 可执行文件装入内存并准备运行时，program 就「变成」process（双击图标 / 在 shell 输入命令）
  • 程序在一个地址空间中执行，不同于真实的内存位置（logical address space）
  • 一个程序可以被多个 process 执行（例如多个用户同时运行同一个编辑器）
  • 一个 process 本身可以是其他程序的执行环境，例如 Java 程序在 JVM 里执行

装入步骤：

  1. 把代码和静态数据（如已初始化的变量）装入内存 / 地址空间
  2. 为运行时 stack 分配内存（C 用它存局部变量、函数参数、返回地址）；填好 main() 的参数 argc、argv
  3. OS 可能为 heap 分配内存（malloc() 申请，free() 显式释放）
  4. 其他初始化，尤其是 I/O：UNIX 上每个 process 默认有三个打开的 file descriptor：standard input、output、error（0、1、2）

1.4 C 程序的内存布局

从低地址到高地址：

区域 例子（课件程序）
text 代码
initialized data int y = 15;（已初始化的全局变量）
uninitialized data int x;（未初始化的全局变量）
heap（向上长） values = (int *)malloc(sizeof(int)*5); 分配的空间
↕ （heap 和 stack 之间的空闲区）
stack（向下长） main 里的局部变量 int *values; int i;
argc, argv（最高） main 的参数
  • global data 分成 initialized 和 uninitialized 两部分
  • argc、argv 有单独的区域

判断题套路：指针变量本身（values）是局部变量在 stack；它指向的那块内存在 heap。

1.5 Process state（必考）

状态 含义
New 正在创建——分配资源
Ready 等待被分配到一个 CPU core
Running 指令正在 CPU 上被取出和执行
Waiting 等待某个（些）事件发生
Terminated 执行结束——回收资源

转移：

  • new → ready：admitted
  • ready → running：scheduler dispatch
  • running → ready：interrupt（如时间片用完）
  • running → waiting：I/O or event wait
  • waiting → ready：I/O or event completion（注意回到 ready，不是直接 running）
  • running → terminated：exit

往年考法：什么事件典型地让进程离开 running 状态？——发出 I/O 请求（→ waiting）。调用普通函数、改局部变量、读 cache 都不会。

（传统 Unix 每个 process 只有一个 thread，所以 process 的状态部分由它当前的活动决定。）

1.6 PCB（Process Control Block / task control block）

每个 process 的相关信息：

字段 内容
Process state running、waiting 等
Program counter 下一条要执行的指令位置
CPU registers accumulators、index registers、stack pointers、通用寄存器、condition codes
CPU scheduling information 优先级、指向调度队列的指针、调度参数
Memory-management information 分配给该进程的内存（复杂结构：paging / segmentation tables）
Accounting information 使用的 CPU、开始以来的时间、时间限制
I/O status information 分配的 I/O 设备、打开文件列表

Linux：kernel 把进程列表存在一个循环双向链表（task list）里；每个元素是一个 process descriptor（PCB），类型 struct task_struct，含 pid、state、time_slice、parent、children、files（打开文件）、mm（地址空间）等。

1.7 Threads 初探

  • 到目前为止假设 process 只有一个执行线程：从第一行到最后一行顺序执行
  • thread 由 PC、registers、execution flags、stack 表示，是 process 的一部分；thread 在 CPU 上执行时，它的状态就在 CPU 的硬件寄存器里
  • 大多数现代 OS 允许一个 process 有多个 thread，同时做多件事（浏览器一个线程显示图片 / 文字，另一个从网络取数据）
  • 多核上，一个 process 的多个 thread 可以并行运行
  • 同一 process 的线程在同一地址空间运行（共享 code、data、files），每个线程有自己的状态（registers、stack、PC）

2 · Process Scheduling

2.1 基本概念

  • 现代 OS 都是 multiprogramming：主要目标是一直有 process 在 CPU 上运行，最大化 CPU 利用率（CPU 比其他设备快得多）
  • Process scheduler：OS 的一种 mechanism，从内存中可用的 process 里选一个在一个 CPU core 上执行
  • 调度准则：CPU 利用率、响应时间、公平、实时保证、延迟（Ch5）
  • 单 CPU 系统上，任何时刻最多只有一个 process / thread 在 CPU 上运行
  • Degree of multiprogramming：当前在内存中的 process 数——决定资源消耗
I/O-bound process CPU-bound process
时间花在 更多在 I/O 更多在计算
CPU burst 很多短的 少数很长的

2.2 Scheduling queues

  • Ready queue：在内存中、就绪、等待执行的 process
  • Wait queues：等待某个事件（如 I/O 完成）的 process
  • process 一生中在各种队列之间迁移

Queueing diagram：ready queue → CPU → 离开 CPU 有四种情况：

  • I/O request → I/O wait queue → I/O → 回 ready queue
  • time slice expired → 直接回 ready queue
  • create child process → child termination wait queue → child terminates → 回 ready queue
  • wait for an interrupt → interrupt wait queue → interrupt occurs → 回 ready queue

2.3 三种 scheduler

Scheduler 作用 频率
Long-term（job scheduler） 选哪些 process 装入内存（分配内存、文件等资源之后）；有一个 job queue 存放提交给 mainframe 的作业；大型机 / 小型机用，PC 不用 很少（秒、分钟）⇒ 可以慢
Short-term（CPU scheduler） 从 ready queue 选下一个执行的 process，分配一个 CPU core 非常频繁（毫秒）⇒ 必须快
Medium-term 需要降低 degree of multiprogramming 时加入：把 process 移出内存存到磁盘，以后再移回来继续执行——swapping（磁盘上的 swap space）
  • Long-term scheduler 决定 degree of multiprogramming
  • 大型机的 long-term scheduler 追求好的 process mix：I/O-bound 和 CPU-bound 混合（全是 I/O-bound 则 ready queue 常空；全是 CPU-bound 则 I/O 设备闲着）

2.4 Context switch（往年选择题）

  • CPU 从一个 process 切换到另一个时，OS 必须保存旧 process 的状态、装入新 process 保存的状态——context switch
  • context 保存在 PCB（或 thread）里，通常包括 registers、PC、stack pointer
  • 图：P0 执行 → interrupt 或 system call → OS save state into PCB0 → reload state from PCB1 → P1 执行（P0 idle）→ 再 interrupt / system call → save into PCB1 → reload from PCB0 → P0 执行
  • Context-switch time 是 overhead：切换期间系统不做有用的工作
    • OS 和 PCB 越复杂，context switch 越长
  • 速度因机器而异：内存速度、要复制的寄存器数、是否有特殊指令（如一条指令 load / store 所有寄存器）
  • 高度依赖底层硬件：有些处理器（如 SUN UltraSPARC）提供多组寄存器，context switch 只需改指针指向另一组寄存器——可以同时装入多个 context

往年考法：关于 context switch 正确的是「OS 保存一个 process / thread 的状态、恢复另一个」。错误选项：「context switch 就是从 user mode 切到 kernel mode」（那是 mode switch，不是 context switch）、「所有 CPU 架构需要相同硬件」、「OS 越复杂 context switch 越短」（反了）。

3 · I/O、Interrupt、DMA 与 Dual Mode

3.1 I/O 的基本操作

  • I/O 设备和 CPU 并发、异步执行
  • 每个 device controller 负责一种设备，有一个 local buffer
  • device controller 负责在外设和它的 local buffer 之间移动数据（I/O 操作是设备 ↔ controller 的 local buffer）
  • CPU 在 main memory 和 local buffer 之间移动数据（通常是键盘、鼠标这类慢设备）
  • device controller 通过 interrupt 通知 CPU 操作完成：输入设备 ⇒ local buffer 里有数据了；输出设备 ⇒ I/O 操作完成

3.2 Interrupt-driven I/O cycle

  1. CPU：device driver 发起 I/O
  2. → I/O controller 开始 I/O
  3. I/O controller：input ready、output complete 或 error，产生 interrupt signal
  4. → CPU 在每条指令之间检查 interrupt；收到 interrupt 后把控制转给 interrupt handler
  5. interrupt handler 处理数据，从 interrupt 返回
  6. CPU 恢复被中断任务的执行
  7. （回到第 1 步，CPU 继续执行并在指令之间检查中断）

Interrupt timeline：CPU 和设备并发；设备给 CPU 发信号触发 interrupt；CPU 处理完 interrupt 后回到被中断的那条指令。

3.3 Interrupt 的功能

  • 现代 OS 广泛用 interrupt 处理异步事件（device controllers、硬件故障）
  • interrupt 把控制转给 interrupt service routine / interrupt handler——kernel 代码的一部分
  • Interrupt priority levels：高优先级的 interrupt 可以抢占低优先级的 interrupt 的处理
  • Trap / exception：软件产生的 interrupt，由错误（如算术错误）或用户请求（如 system call）引起
  • 所有现代 OS 都是 interrupt-driven；现代计算机每秒发生数百次 interrupt

往年考法：关于 interrupt 错误的是「所有 interrupt 都以完全相同的方式处理、没有优先级差别」——实际有 priority levels。interrupt 可由硬件产生、也可由软件异常 / trap 产生、由 kernel 处理——都对。

3.4 DMA（Direct Memory Access）

  • Programmed I/O：CPU 运行特殊 I/O 指令，一次一个字节在内存和慢设备（键盘、鼠标）之间搬
  • 为避免 programmed I/O，对快设备和大量数据用 DMA controller：绕过 CPU，直接在 I/O 设备和内存之间传数据——CPU / OS 初始化 DMA controller，之后 DMA controller 负责搬数据，CPU 不参与
    • 把 CPU 从慢速数据搬运中解放出来
  • OS 在内存中写 DMA command block：源地址和目的地址、读或写模式、传输字节数；把 command block 的位置写给 DMA controller
  • Bus mastering：DMA controller 从 CPU 抢占 bus
  • 完成后给 CPU 发 interrupt 表示完成

DMA 传输的六步：

  1. device driver 被告知要把磁盘数据传到地址 X 处的 buffer
  2. device driver 告诉 disk controller 从磁盘传 C 个字节到地址 X 的 buffer
  3. disk controller 发起 DMA 传输
  4. disk controller 把每个字节发给 DMA controller
  5. DMA controller 把字节传到 buffer X，内存地址递增、C 递减，直到 C = 0
  6. C = 0 时，DMA interrupt CPU 表示传输完成

往年考法：关于 DMA 正确的是「DMA 让设备与内存之间的数据传输更少需要 CPU 参与」。错误选项：「DMA 用于慢设备、CPU 用于快设备」（反了）、「DMA 完全消除了 interrupt」（完成时仍要 interrupt）、「CPU 和 DMA 不能并发执行」（可以）。

3.5 Dual-mode operation

  • 让 OS 保护自己和其他系统组件：区分 OS（kernel）代码和用户代码的执行（applications、standard libs 在 user mode；kernel 在 kernel mode；下面是 hardware）
  • 基本手段：保护 OS 不被出错的用户破坏、保护用户之间互不破坏
  • 硬件提供 mode bit：user mode = 1，kernel mode = 0
  • 某些指令是 privileged，只能在 kernel mode 执行：I/O control、timer management、interrupt management
  • 在 user mode 执行 privileged 指令 ⇒ 硬件视为非法，trap 到 OS

扩展到多于两个 mode：

  • Intel 处理器有四个保护环：ring 0 = kernel mode，ring 3 = user mode；ring 1、2 可用于 OS 服务，实际很少用
  • ARMv8 有 7 个 mode
  • 支持虚拟化的 CPU 常有单独的 mode 表示 VMM 在控制：VMM 的权限比用户进程多、比 kernel 少
  • 类似 context switch，VMM 要在不同 VM 之间做 machine switch：保存一个 OS 的整个机器状态（registers、PC，并且不同于 context switch，还包括所有特权硬件状态），恢复新 VM 的机器状态，跳到新 VM 的 PC（可能在 OS 内部，也可能在用户进程里）

Mode 的转换：

  • 初始控制在 OS（kernel mode）；把控制交给用户程序时设为 user mode
  • 最终通过 interrupt、trap 或 system call 回到 OS
  • 怎么保证用户程序一定会把控制还给 OS？——timer（定时产生 interrupt，防止死循环霸占 CPU）
  • 用户程序请求服务（system call）时，从 user mode 转到 kernel mode；从 system call 返回时重设为 user mode

3.6 三种 mode transfer

类型 触发 同步 / 异步 例子
System call 用户进程请求 OS 服务 同步（程序主动） exit()、write()、read()——像函数调用，但在用户进程「外面」
Interrupt 外部事件 异步，与用户进程无关 timer、I/O
Trap / Exception 进程内部事件 同步 protection violation（segmentation fault）、算法错误（除以 0）

4 · Operations on Processes

4.1 Process tree

  • 系统中的 process 并发执行，动态创建和删除；OS 要提供 process creation 和 process termination 的机制
  • parent process 创建 child process，child 又可以创建 child ⇒ 进程树
  • 常见：桌面本身是 parent process，双击图标或在 shell 输入命令，就创建它的 child process
  • Linux 进程树：根是 systemd（pid = 1），下面有 logind、python、sshd 等；logind → bash → ps、vim；sshd → sshd → tcsh

4.2 Process creation

  • 大多数 OS（UNIX、Linux、Windows）用唯一的 pid（整数）标识进程
  • child 需要资源（CPU 时间、内存、文件、I/O 设备）；parent 可以给 child 传初始化数据

资源共享的三种选择：

  • parent 和 children 几乎共享所有资源——fork()
  • children 只共享 parent 的一部分资源——clone()（Ch4）
  • parent 和 children 不共享资源

执行的两种选择：

  • parent 与 children 并发执行（如 shell 运行 a.out &）
  • parent 等待某些或全部 children 结束（如 shell 等 a.out 完成）

地址空间的两种选择：

  • child 是 parent 的副本（同样的程序和数据）——Unix / Linux
  • child 装入一个新程序

4.3 fork() / exec() / wait()

  • fork() 创建新进程，复制 parent 的整个地址空间；两个进程都从 fork() 之后的下一条指令继续执行
  • exec() 在 fork() 之后用来用新程序替换 child 的地址空间
  • parent 调用 wait() 等待 child 结束

fork() 的返回值（核心）：每个进程各收到一个返回值

返回值 在哪个进程 含义
> 0 原来的 parent 这个正整数是新建 child 的 pid
= 0 新建的 child
< 0（−1） 原来的进程 出错，child 没有创建成功（errno 指示原因）
  • child 复制 parent 的所有状态：内存（程序和数据）、file descriptors 等——每个进程有自己的一份程序和数据（耗时）

UNIX fork 的实现步骤：

  1. 在 kernel 中创建并初始化 PCB
  2. 创建新的地址空间（分配内存）
  3. 用 parent 地址空间的全部内容的副本初始化它（耗时）
  4. 继承 parent 的执行上下文（如打开的文件）
  5. 通知 CPU scheduler：新的 child 已经 ready

fork 之后 parent 与 child：

相同（复制） 不同
address space PID
global & local variables fork() 的返回值
current working directory running time
root directory running state
process resources、resource limits
Program Counter（PC）

其他 system calls：

  • exec()、execlp()…：改变当前进程运行的程序，从可执行文件创建新的 process image
  • wait()：等待（child）进程结束，或一般地等待某个事件
  • exit()：终止当前进程并释放所有资源
  • signal()：给另一个进程发通知

典型程序：

int main() {
    pid_t pid = fork();            /* fork another process */
    if (pid < 0) {                 /* error occurred */
        fprintf(stderr, "Fork Failed");
        exit(-1);
    } else if (pid == 0) {         /* child process */
        execlp("/bin/ls", "ls", NULL);
    } else {                       /* parent process */
        wait(NULL);                /* wait for the child to complete */
        printf("Child Complete");
        exit(0);
    }
}

实现一个 shell：循环读入并解析命令行 → fork() → child 里 exec(prog, args)（不会返回）→ parent wait(child_pid)。

4.4 数进程（考试重点）

方法：画树，或者看「每个进程在每一轮变成几个」。

例 1（课件）：

for (int i = 0; i < 10; i++) {
    fork();
    fork();
}

每轮：每个进程连 fork 两次 ⇒ 变成 2×2=4 个，而且所有进程都继续循环 ⇒ 共 410 个进程。

例 2（课件）：

for (int i = 0; i < 10; i++)
    if (fork())
        fork();

每轮：fork() 后，parent（返回值 > 0）再 fork 一次；child（返回值 0）不再 fork ⇒ 每个进程变成 3 个，所有进程都继续循环 ⇒ 共 310 个。

例 3（往年选择题，改写）：

for (i = 0; i < 3; i++) {
    if (fork() == 0) { fork(); printf("X "); return 1; }
}
printf("Y ");
  • 只有原进程在循环：每轮它 fork 出一个 child；child 再 fork 一次，两个都打印 X 然后 return（不再循环）
  • 3 轮 ⇒ 新进程 3×2=6 个，各打印一次 X；原进程最后打印一次 Y
  • 共 7 个进程，X 打印 6 次，Y 打印 1 次

例 4（往年大题，改写）：

for (int i = 0; i < n; i++) {
    if (fork()) fork();
    else break;
}

每轮，每个还在循环中的进程：

  • 第一次 fork() 产生的 child 进入 else，break（不再循环）
  • parent 进入 if，再 fork() 一次；这次的 child（以及 parent）继续循环

⇒ 每个活跃进程：这一轮后变成 3 个，但只有 2 个继续。设第 k 轮前活跃进程数为 Ak：Ak+1=2Ak，A0=1 ⇒ Ak=2k。

  • 第 k 轮 break 掉的新进程数 =2k
  • n 轮后：活跃的 2n 个；break 掉的 1+2+⋯+2n−1=2n−1 个
  • 总进程数 =2n+(2n−1)=2n+1−1；break 执行次数 =2n−1

n=2：7 个进程，break 3 次（我用程序模拟验证：n=1,2,3,4 依次 3、7、15、31）。进程树：P0 的 children 是 P1、P2、P3、P4；P2 的 children 是 P5、P6。break 掉的是 P1、P3、P5（每次第一个 fork 出来的 child）。

数进程的套路：

  1. 区分哪些进程继续循环、哪些 break / return / exec 了
  2. 看每个继续循环的进程在一轮中变成几个
  3. 打印次数 = 执行到那条 printf 的进程数

4.5 fork + exec 的输出（往年大题，改写）

int ret = fork();
if (ret == 0) {
    printf("Hello1\n");
    exec("some_executable");
    printf("Hello2\n");
} else if (ret > 0) {
    wait(NULL);
    printf("Hello3\n");
} else {
    printf("Hello4\n");
}

要考虑 system call 成功和失败的所有情况（exec 成功则替换进程映像、不返回；失败返回 −1、继续往下执行）：

情况 输出
fork 成功、exec 成功 Hello1、Hello3（Hello2 不会打印：程序已被替换）
fork 成功、exec 失败 Hello1、Hello2、Hello3
fork 失败 Hello4

（因为 parent wait 了 child，Hello3 一定在 child 的输出之后。）

4.6 关于 fork 的补充

  • Unix 的进程创建很特别：大多数 OS 在新地址空间创建进程、读入可执行文件、开始执行——一步完成；Unix 把它拆成两个 system call：fork() 和 exec()
  • Linux 用 copy-on-write（COW）实现 fork（Ch10）：不复制地址空间，parent 和 child 共享一份，child「指向」parent 的地址空间
    • 把复制推迟到内容被修改（写）时；如果从不写——例如 fork() 后立刻 exec()——就根本不用复制
    • 大大简化并加速进程创建
  • Linux 也通过 clone() 实现 fork：用一组 flags 指定 parent 和 child 共享哪些资源（Ch4）

4.7 Process termination

  • 进程执行完最后一条语句，用 exit() 请求 OS 删除它
    • 可以通过 parent 的 wait() 返回一个状态值（通常是整数）
    • 大部分资源（内存：program、data、heap、stack；打开的文件；I/O buffer）被 OS 回收
  • parent 可以终止 children：Unix / Linux 用 abort()，Windows 用 TerminateProcess()
    • parent 要知道 child 的 PID——创建时 fork() 正好把它返回给 parent
  • parent 终止 child 的原因：
    • child 超出了分配的资源
    • 分配给 child 的任务不再需要
    • parent 要退出，而有的 OS 不允许 parent 终止后 child 继续存在

Cascading termination：有的 OS 不允许没有 parent 的 child 存在——一个进程终止，它所有的 children 也必须终止，由 OS 发起。

  • 正常终止时会直接或间接调用 exit()（C runtime 库默认会调用 exit()）
  • parent 用 pid = wait(&status); 等待 child：得到 child 的退出状态和已终止 child 的 pid（知道是哪个 child 结束了）

4.8 Zombie 与 Orphan（往年选择题）

  • 进程终止时资源被 OS 回收；但还有清理工作要由 parent 和 OS 完成：它在 process table（kernel 中记录所有进程的结构）里的条目要保留到 parent 调用 wait()，因为条目里有该进程的退出状态

Zombie process：已经终止、但 parent 还没调用 wait() 的进程——它在 process table 中的条目、process ID、PCB 仍然存在，其他资源都已释放；不可运行（没有地址空间了，程序和数据都已删除）。

  • 所有进程终止前都会经过 zombie 状态，但一般只存在很短时间
  • parent 调用 wait() 后，zombie 的 pid、process table 条目和 PCB 才被释放

Orphan：parent 没调用 wait() 就终止了，child 成为 orphan——它可能仍可运行（如果没有 cascading termination），或者最终成为 zombie。

  • 必须有机制给 orphan 重新指定 parent，否则没有 parent 的已终止进程会永远是 zombie，浪费内存
  • init（或 systemd） 被指定为 orphan 的 parent，它定期调用 wait()，收集 orphan 的退出状态并释放其 pid 和 process table 条目

往年考法：关于 zombie 正确的是「已经终止、但 parent 还没收集它的状态」。错误选项：「zombie 还在正常执行用户代码」、「exec() 失败时产生 zombie」、「zombie 没有 process identifier」（它的 pid 还在）。

5 · Interprocess Communication（IPC）

5.1 为什么要合作

  • 进程可以是 independent 或 cooperating；cooperating 进程能影响或被其他进程影响（如共享数据）
  • 合作的理由（多线程进程中也自然存在）：
    • Information sharing：多个应用对同一信息感兴趣（复制粘贴）
    • Computation speedup：并行执行任务 / 子任务（如机器学习）
    • Modularity：功能分到不同进程 / 线程
  • cooperating 进程需要 IPC 机制交换数据。两种模型：
模型 做法
Shared memory 共享一块内存区域，进程通过读写共享区域交换信息
Message passing 通过合作进程之间交换消息显式通信（消息经过 kernel 的 message queue）

5.2 Producer–Consumer（shared memory）

  • producer 产生信息，consumer 消费
  • unbounded buffer：buffer 大小没有实际限制；bounded buffer：固定大小

Bounded buffer 的共享数据：

#define BUFFER_SIZE 10
typedef struct { ... } item;
item buffer[BUFFER_SIZE];
int in = 0;   /* 下一个空位 */
int out = 0;  /* 第一个满位 */

Producer：

while (true) {
    /* produce an item in next_produced */
    while (((in + 1) % BUFFER_SIZE) == out)
        ; /* do nothing：buffer 满 */
    buffer[in] = next_produced;
    in = (in + 1) % BUFFER_SIZE;
}

Consumer：

while (true) {
    while (in == out)
        ; /* do nothing：buffer 空 */
    next_consumed = buffer[out];
    out = (out + 1) % BUFFER_SIZE;
    /* consume the item in next_consumed */
}
  • 这个方案简单且正确，但同一时刻最多只能有 BUFFER_SIZE - 1 个 item

为什么少一个？ 用 in == out 表示空；如果允许放满 BUFFER_SIZE 个，满的时候 in 也会追上 out，变成 in == out，和空无法区分。所以约定 (in + 1) % BUFFER_SIZE == out 就算满，空出一格。（加一个计数器就能用满全部格子——Ch6 会看到这又带来 race condition。）

5.3 Message passing

  • 进程不共享地址空间就能通信和同步；在分布式环境中特别有用
  • IPC facility 提供两个操作：send(message)、receive(message)；消息大小可以固定或可变
  • （跨网络通信看起来就像文件 I/O：write(wfd, wbuf, wlen) / read(rfd, rbuf, rmax)）
  • P 和 Q 要通信：建立 communication link，再用 send() / receive() 交换消息

实现 link 和 send / receive 的几个维度：

  • Direct or indirect communication
  • Synchronous or asynchronous communication
  • Automatic or explicit buffering

5.4 Direct vs Indirect communication

Direct Indirect
原语 send(P, message)：发给进程 P；receive(Q, message)：从 Q 收 send(A, message)：发到 mailbox A；receive(A, message)：从 mailbox A 收
link 的建立 每对想通信的进程之间自动建立；只需知道对方身份 只有两进程共享一个 mailbox 时才有 link
一条 link 关联 恰好一对进程 可以多于两个进程
每对进程之间 恰好一条 link 可以有多条 link（每条对应一个 mailbox）
缺点 模块化差：改一个进程的 id，可能要检查所有合作进程
  • mailbox（也叫 port）每个有唯一 id；OS 要提供：创建 mailbox、通过 mailbox 收发消息、销毁 mailbox

Mailbox sharing 问题：P1、P2、P3 共享 mailbox A，P1 发送，P2 和 P3 都 receive——谁收到？解决办法：

  • 一条 link 最多关联两个进程
  • 同一时刻只允许一个进程执行 receive()
  • 让系统任意选一个接收者，并告诉 sender 接收者是谁

5.5 Synchronization（blocking / non-blocking）

Blocking（synchronous） Non-blocking（asynchronous）
send sender 阻塞直到消息被接收进程或 mailbox 收到 sender 发出消息后立即继续
receive receiver 阻塞直到有消息可用 receiver 取到一条有效消息或 null
  • send 和 receive 都 blocking 时，sender 和 receiver 之间形成 rendezvous（会合）
  • 这时 producer–consumer 问题变得很简单：producer 只管 send(next_produced)，consumer 只管 receive(next_consumed)

5.6 Buffering

无论 direct 还是 indirect，消息都放在一个临时队列里，三种实现：

容量 行为
Zero capacity 队列里不存消息；sender 必须等 receiver（rendezvous）
Bounded capacity 长度有限 n；link 满时 sender 要等
Unbounded capacity 无限长；sender 从不等

5.7 Pipes

最早的 IPC 机制之一（早期 UNIX）。实现 pipe 要考虑四个问题：

  1. 单向还是双向？
  2. 双向的话，是 half duplex（同一时刻只能一个方向）还是 full duplex（两个方向同时）？
  3. 通信的进程之间必须有关系（如 parent–child）吗？
  4. 能跨网络用，还是只能在同一台机器上？
Ordinary pipes Named pipes
方向 单向（unidirectional） 双向
关系 需要 parent–child 关系（parent 创建 pipe，再 fork() 出 child 来用） 不需要 parent–child 关系；多个进程可以用（通常有多个 writer）
访问 不能从创建它的进程外部访问 不需要亲缘关系就能访问
生命周期 进程通信完、终止后就不存在了 进程结束后仍存在，直到显式删除
机器 同一台机器 UNIX：同一台；Windows：可以跨机器
UNIX pipe(int fd[])；写端 fd[1]、读端 fd[0] FIFO，用 mkfifo() 创建，在文件系统里像普通文件；只支持 half-duplex（双向同时传要用两个 FIFO）
Windows anonymous pipes，用 ReadFile() / WriteFile() CreateNamedPipe()；full-duplex，可以跨机器

Ordinary pipe 的用法：

  • 标准 producer–consumer：producer 写写端 fd[1]，consumer 读读端 fd[0]
  • UNIX 把 pipe 当成特殊文件，用标准 read() / write()；child 继承 parent 的 pipe
  • parent 先 pipe() 再 fork()，child 继承包括 pipe 在内的一切
  • 如果 parent 写、child 读：parent 必须显式关闭读端，child 必须显式关闭写端

为什么要关掉不用的那一端？ 读端的 read() 只有在所有写端都关闭后才会返回 EOF；如果 reader 自己还开着写端，它永远等不到 EOF。

int pfds[2]; char buf[30];
pipe(pfds);                     /* create a message pipe */
pid_t pid = fork();             /* 0 (child), non-zero (parent) */
if (pid != 0) {
    printf("PARENT: writing to pipe\n");
    close(pfds[0]);             /* parent 不读，关读端 */
    write(pfds[1], "test", 5);
    wait(NULL);                 /* wait until the child returns */
    printf("PARENT: exiting\n");
} else {
    printf("CHILD: reading from pipe\n");
    close(pfds[1]);             /* child 不写，关写端 */
    read(pfds[0], buf, 5);
    printf("CHILD: read \"%s\"\n", buf);
}

往年考法（选择）：关于 ordinary pipe 错误的是「可以被任意进程访问」——ordinary pipe 不能从创建它的进程外部访问。可以像 file descriptor 一样访问、进程终止后消失、通常用于 parent–child——都对。

往年考法（填空，改写）：parent 和 child 各数一个文件里的偶数个数，child 通过 pipe 把结果传给 parent。关键空：

  • 把打开的文件变成标准输入，这样能用 scanf：先 close(0)，再 dup(fin)（dup 返回最小的空闲 fd，也就是刚关掉的 0）
  • 计数：if (number % 2 == 0) cnt++
  • child 写：write(fd[1], &cnt, sizeof(int))（写端、传地址）
  • parent 读：read(fd[0], &child_cnt, sizeof(int))（读端）

6 · Client–Server Communication

6.1 Sockets

  • Socket = 通信的端点；网络上通信的一对进程用一对 socket
  • socket 由 IP address + port number 唯一标识（port 指定 client 或 server 上的进程 / 应用）
  • server（一直运行）监听指定（well-known）端口等待 client 请求；收到请求后可以 accept，建立 socket 连接

细节：

  • 服务器（SSH、FTP、HTTP）监听 well-known ports：SSH 22、FTP 21、HTTP 80；1024 以下的端口都是 well-known，保留给标准服务
  • server 的地址（IP，或名字经 DNS 解析成 IP）和端口是公开的；server 总在等 client 联系
  • 只有 client 能发起通信
  • client 发起连接时知道自己的 IP，选一个大于 1024、未被使用的端口
  • IP address 全球唯一：IPv4 32 位（如 128.32.244.172），IPv6 128 位
  • 4-tuple（source IP, source port, destination IP, destination port）唯一确定一对通信

6.2 RPC（Remote Procedure Call）

  • 最常见的远程服务形式之一：在网络连接的系统之间使用的过程调用机制
  • 基于消息的通信方案，提供远程服务
  • 常用于实现分布式文件系统（一组 RPC daemons 和 clients）

8 · 易错点

  • waiting 状态结束后回到 ready，不是直接回 running。
  • running → ready 是 interrupt（时间片到），running → waiting 是 I/O / event wait。
  • Context switch（换进程）≠ mode switch（user ↔ kernel）。
  • OS / PCB 越复杂，context switch 越慢。
  • fork() 在 child 返回 0，在 parent 返回 child 的 pid，失败返回 −1（此时没有 child）。
  • exec() 成功不返回，它后面的代码不会执行；失败才会继续往下走。
  • Zombie 还有 pid 和 PCB，只是其他资源都释放了；它不可运行。
  • Ordinary pipe 单向、要 parent–child、不能被外部进程访问；UNIX named pipe（FIFO）是 half-duplex。
  • Pipe：fd[0] 读，fd[1] 写。
  • Mode bit：user = 1，kernel = 0。
  • DMA 结束时仍然要 interrupt CPU。
  • Bounded buffer 方案最多放 BUFFER_SIZE − 1 个。
