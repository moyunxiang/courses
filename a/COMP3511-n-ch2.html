1 · Operating System Services

OS 为程序执行和其他对程序 / 用户的服务提供环境。

1.1 对用户有帮助的服务

服务 说明
User interface 几乎所有 OS 都有 UI：CLI、GUI、touch-screen
Program execution 把程序装入内存并运行，正常或异常（报错）结束
I/O operations 运行中的程序可能需要 I/O（文件或 I/O 设备）
File-system manipulation 读写文件和目录、搜索、创建、删除、列出信息、权限管理
Communications 进程间交换信息（同一台机器或跨网络）；通过 shared memory 或 message passing（由 OS 移动 packet）
Error detection OS 要时刻注意可能的错误：CPU 和内存、I/O 设备、用户程序中都可能出错；对每类错误采取适当措施，保证计算正确一致；调试工具能大大提高效率

1.2 保证系统自身高效运行的服务（通过资源共享）

服务 说明
Resource allocation 多用户 / 多作业并发运行时，给每个分配资源：CPU cycles、memory、file storage、I/O devices
Logging 记录哪些用户用了多少、哪种资源
Protection and security Protection：保证对系统资源的所有访问都受控制；并发进程互不干扰。Security：防外部入侵——需要 user authentication，还要防止对外部 I/O 设备的非法访问

往年考法：判断 OS services 的说法。「错误只出现在内存和 I/O 设备」是错的——错误还会出现在 CPU 和用户程序中。logging 记录各用户使用的资源、resource allocation 分配 CPU / 内存 / 文件存储、UI 可以是 CLI 或 GUI——这些都对。

（课件图 A View of OS Services：最上 user and other system programs → user interfaces（GUI、touch screen、command line）→ system calls → services（program execution、I/O、file systems、communication、resource allocation、accounting、error detection、protection and security）→ operating system → hardware。）

2 · User–OS Interface

三种方式：CLI（command interpreter）、GUI、touch screen。

2.1 CLI

  • 用户直接输入命令让 OS 执行
  • 有时在 kernel 里实现，有时由 system programs 实现
  • 有时有多种版本——Unix / Linux 里叫 shells（C shell、Bourne-Again shell（bash）、Korn shell……）
  • Shell 的主要功能：(1) 取用户命令；(2) 解释它；(3) 执行它

2.2 GUI

  • 用户友好的桌面隐喻界面：鼠标、键盘、显示器；图标代表文件、程序、目录、系统功能；鼠标按键触发各种动作
  • 1970 年代初 Xerox PARC 发明，首先在 Apple Macintosh（1984）广泛使用
  • 许多系统 CLI 和 GUI 都有：Windows 是 GUI + CLI「command」shell；Mac OS X 是 Aqua GUI，底下是 UNIX kernel，也有 shell；Unix / Linux 是 CLI + 可选 GUI（KDE、GNOME）

2.3 Touchscreen

  • 不能 / 不想用鼠标；基于手势的操作和选择；虚拟键盘；语音命令（iPhone Siri）

3 · System Calls

3.1 是什么

  • System calls 提供 OS 服务的编程接口
  • 一般是用高级语言（C/C++）写的函数；某些需要直接访问硬件的底层任务用汇编写
  • 例：cp in.txt out.txt 需要一连串 system call：获取输入文件名（写提示到屏幕、接受输入）→ 获取输出文件名 → 打开输入文件（不存在就 abort）→ 创建输出文件（已存在就 abort）→ 循环：读输入文件、写输出文件（直到读失败）→ 关闭输出文件 → 在屏幕写完成信息 → 正常终止

（一个简单的复制命令背后有十几个 system call——这正说明为什么要 API 来简化。）

3.2 API

  • API（Application Program Interface）：规定应用程序员可以使用的一组函数，包括传入的参数和期望的返回值
  • API 中的函数代表程序员去调用真正的 system call
    • 例：Windows 的 CreateProcess() 调用 Windows kernel 里的 NTCreateProcess() system call
  • 程序员通过 OS 提供的库访问 API；UNIX / Linux 的 C 程序用 libc
  • 三种最常见的 API：
    • Win32 API（Windows）
    • POSIX API（POSIX 系统：几乎所有 UNIX、Linux、Mac OS X）
    • Java API（JVM）

标准 API 例（#include <unistd.h>）：

ssize_t read(int fd, void *buf, size_t count);
  • int fd：要读的 file descriptor
  • void *buf：读入数据的缓冲区
  • size_t count：最多读多少字节
  • 返回值：0 表示 end of file；−1 表示出错；（否则是实际读到的字节数）

3.3 为什么用 API 而不直接调用 system call（往年选择题）

  • Program portability：用某个 API 写的程序可以在任何支持同一 API 的系统上编译运行——而 system call 的实现因机器而异
  • 隐藏 system call 的复杂细节：实际的 system call 往往比 API 更细、更难用
  • API 的调用者不需要知道 system call 怎么实现、执行时做什么，只需遵守 API 的格式、理解 OS 会做什么

往年考法：API 的优点是「更方便的编程接口」。干扰项：「API 总比 system call 快」（错，API 最终还是要调 system call）、「API 能绕过 kernel 保护」（错）、「API 不需要 linker / loader」（错）。

3.4 System call 的实现

  • 大多数语言的 run-time environment（RTE）（库里的一组函数）提供 system-call interface，作为到 OS system call 的链接
  • 每个 system call 有一个编号；system-call interface 维护一张按编号索引的表
  • System-call interface 的功能：
    • 拦截 API 中的函数调用
    • 调用 OS 中相应的 system call
    • 返回 system call 的状态和返回值（如果有）

API – System Call – OS 关系图：user application 在 user mode 调用 open() → system call interface（跨到 kernel mode）→ 查表第 i 项 → 执行 open() 的实现 → return 回到用户程序。调用者对 system call 怎么实现一无所知。

3.5 参数传递的三种方法

除了 system call 编号，通常还要传更多信息（类型和数量因 OS 和调用而异）：

方法 做法 限制
Registers 最简单，参数直接放在寄存器里 参数可能比寄存器多
Block（table）method 参数存在内存中的一个 block / table 里，block 的地址放在寄存器里传 不限制个数和长度
Stack method 程序把参数 push 到栈上，OS 再 pop 出来 不限制个数和长度

图（Parameter Passing via Table）：用户程序把参数存在 X 处，「load address X」到寄存器，调用 system call 13；OS 的 system call 13 代码「use parameters from table X」。

3.7 Standard C Library 例：printf() 和 write()（往年选择题）

C 程序调用 printf("Greetings")（library call，在 user mode）→ standard C library 调用 write() system call（进入 kernel mode）→ 返回。

往年考法：printf() 和 write() 的关系——printf() 调用 write() system call 来获得 OS 服务。printf() 不是 system call；调用 printf() 的那一刻不会立即进入 kernel mode（要等库里调到 write() 才进）；write() 不会调用 printf()。

4 · System Programs

  • 现代计算机的另一面：一组 system services（system programs、system utilities），为程序开发和执行提供方便的环境
  • 有的只是 system call 的用户界面，有的复杂得多
  • 大多数用户看到的 OS 是由 application 和 system programs 定义的，而不是实际的 system call
  • 例：鼠标窗口的 GUI 和 UNIX 命令行 shell 用的是同一套底层 system call，但对用户看起来、用起来完全不同

类别：

类别 内容
File management 创建、删除、复制、重命名、打印、dump、列出、操作文件和目录
Status information 日期、时间、可用内存、磁盘空间、用户数；详细的性能、日志、调试信息
File modification 文本编辑器；搜索文件内容或变换文本的命令
Programming-language support C、C++、Java、Python 等的编译器、汇编器、调试器、解释器
Program loading and execution absolute / relocatable loaders、linkage editors、overlay-loaders、调试系统
Communications 在进程、用户、计算机之间建立虚拟连接：发消息、浏览网页、发邮件、远程登录、传文件
Background services 开机启动；有的完成任务就终止，有的一直运行到关机——叫 services、subsystems、daemons；如磁盘检查、进程调度、错误日志
Application programs 不属于 OS；由命令行、鼠标点击、手指点按启动；如浏览器、文字处理、表格、数据库、游戏

5 · Linkers and Loaders

  • 源代码编译成 relocatable object files（可装到任何物理内存位置）
  • Linker 把这些 object files（以及需要的库）合成一个 binary executable file
  • 程序以 binary executable 的形式存在 secondary storage 上，要由 loader 装入内存才能执行
  • Relocation：给程序各部分分配最终地址，并调整代码和数据以匹配这些地址（后面讲）
  • 现代通用 OS 不把库静态链接进可执行文件，而是用 dynamically linked libraries（Windows 叫 DLL）：需要时才装入，所有使用同一版本该库的程序共享（只装一次）
  • object file、executable file 有标准格式（机器码 + 符号表），OS 才知道怎么装入和启动

流程图：

main.c→gcc -c main.c (compiler)main.o→gcc -o main main.o -lm (linker，+ other object files)main→./main (loader，+ dynamically linked libraries)program in memory

6 · OS Design and Implementation

6.1 设计目标

  • OS 的设计和实现没有「标准答案」，但有些方法被证明是成功的
  • 内部结构差异很大；高层设计受硬件选择和系统类型（桌面 / 笔记本、移动、分布式、实时）影响
  • 从定义目标和规格开始：
目标
User goals 方便使用、易学易用、可靠、安全、快
System goals 易于设计、实现、维护；灵活、可靠、无错、高效
  • 设计 OS 是高度创造性的软件工程任务

6.2 Policy vs Mechanism（重要原则）

  • Policy：What will be done?（做什么）
  • Mechanism：How to do it?（怎么做）
  • 例：timer 是保证 CPU protection 的 mechanism；给某个用户设多长时间是 policy
  • 分离的好处：policy 改变时有灵活性（而 policy 经常会变）。分离得好，同一套机制既能支持「I/O 密集型程序优先于 CPU 密集型」，也能支持相反的 policy
  • 一句话：OS 有特定目标 → 目标决定 policy → OS 用具体的 mechanism 实现 policy

6.3 Implementation

  • 早期 OS 用汇编写；现在大多用 C / C++，kernel 最底层可能仍用汇编
  • 常常不止一种高级语言：Android 系统库多用 C / C++，应用框架主要用 Java
  • 高级语言的优点：更容易移植到其他硬件；写得更快、更紧凑、更易理解和调试
  • 唯一可能的缺点：速度降低、存储需求增加——对今天的计算机不是大问题

7 · 例子

7.1 MS-DOS（单任务）

  • Single-tasking；开机时调用 shell
  • 运行程序很简单：不创建进程；单一内存空间
  • 把程序装入内存，覆盖除 kernel 外的一切（包括 shell 的大部分）
  • 程序退出 → 重新装入 shell

7.2 FreeBSD（多任务，Unix 变种）

  • 用户登录时调用用户选的 shell
  • shell 执行 fork() 创建新进程；执行 exec() 把新程序装入该进程
  • shell 等待进程结束，或者继续接受用户命令（后台运行）
  • OS 因此需要 CPU scheduling、进程协调、内存管理等，以支持 multiprogramming 和 multitasking

8 · Operating System Structure（重点）

通用 OS 是非常大的程序，有多种组织方式。

8.1 Simple structure（MS-DOS）

  • 没有清楚定义的结构，通常从小而简单、功能有限的系统开始
  • MS-DOS：用最小空间提供最多功能；没有仔细划分模块
  • 有一些结构，但接口和功能层次没有很好分离——例如应用程序可以直接访问 I/O
  • 为 Intel 8088 写的，没有 dual mode（kernel / user mode），没有硬件保护

8.2 Monolithic structure（original UNIX）

  • 传统 UNIX 中，kernel 是 system-call interface 以下、物理硬件以上的一切
  • 早期 UNIX 受硬件功能限制，结构有限
  • 把 kernel 的所有功能放进一个单一的、静态的二进制文件，在单一地址空间中运行——monolithic structure
  • UNIX 分两部分：kernel 和 system programs；kernel 又分成一系列接口和 device drivers（随着 UNIX 演进扩展了很多）
  • 缺点：大量功能放在一个层次里，难以实现、调试和维护
  • 优点：性能有明显优势——system-call interface 开销很小，kernel 内部通信很快
  • 因为速度和效率，UNIX、Linux、Windows 仍在用

图：(the users) → shells and commands、compilers and interpreters、system libraries → system-call interface to the kernel → [kernel：signals terminal handling、character I/O system、terminal drivers | file system、swapping、block I/O system、disk and tape drivers | CPU scheduling、page replacement、demand paging、virtual memory] → kernel interface to the hardware → terminal controllers、device controllers、memory controllers。

8.3 Linux

  • 基于 UNIX，结构类似
  • Linux kernel 是 monolithic 的：完全在 kernel mode、单一地址空间运行
  • 应用通过 glibc 标准 C 库与 system call interface 通信
  • 有 modular 设计，允许在运行时修改 kernel（LKM）

8.4 Modular design

  • Monolithic 常被称为 tightly coupled：改一部分会影响其他部分——本质上是一个在单一地址空间运行的大程序
  • 设计 loosely coupled 的系统：分成独立的、更小的组件，每个功能明确有限
  • 优点：改一个组件只影响它自己，创建和修改组件更自由灵活
  • 做成 modular 有很多方法，layered approach 是其中之一

8.5 Layered approach

  • OS 分成若干层，每层建在下层之上：最底层（layer 0）是硬件，最高层（layer N）是用户界面
  • 每层由数据结构和一组函数组成，可被上层调用，它又可调用下层的操作
  • 每层用下层的服务、提供一组函数、给上层提供服务

Information hiding：一层不需要知道下层操作怎么实现，只需知道做什么（接口）；每层对上层隐藏自己的数据结构、操作和硬件。

优点：构造和调试简单——从最低层开始逐层调试（调第 k 层时，下面各层已经验证过，出错一定在这一层）。在其他软件系统中很成功，如计算机网络（TCP/IP/link/physical）、web 应用。

为什么很少 OS 用纯分层：

  • 很难合理地定义各层和它们的功能（例如 memory management 和 file system 互相需要对方）
  • 性能：一个程序要穿过多层才能拿到服务，开销大
  • 趋势：更少的层、每层更多功能、模块化代码，避免复杂的层定义和交互

往年考法：关于 layered design 正确的是「相邻层之间的接口通常定义得很清楚」。错误选项：「任何层可以直接访问任何层」（只能用下层）、「消除了所有性能开销」（恰恰相反）、「纯分层是所有现代 OS 的主流结构」（很少用）。

8.6 Microkernel

  • kernel 变得太大、难管理 ⇒ 把所有非必要组件移出 kernel，作为 system 或 user-level 程序在独立的地址空间中实现 ⇒ kernel 小得多
  • Mach（CMU，1980 年代中期）用 microkernel 方法模块化了 kernel
  • 最著名的 microkernel OS 是 Darwin（Mac OS X 和 iOS 用），由两个 kernel 组成，其一是 Mach microkernel
  • 哪些服务留在 microkernel、哪些放到用户空间没有共识，但通常 microkernel 提供最少的进程和内存管理 + 通信机制

主要功能：通过 message passing，在程序和运行在用户空间的各种服务之间提供通信。例：应用要访问文件，必须和 file server 交互；程序和服务从不直接交互，而是通过 microkernel 交换消息间接通信。

优点 缺点
容易扩展：新服务通常加在用户空间，不需要修改 kernel 性能可能严重下降：system-function 开销增加，用户空间与 kernel 空间之间的通信
必须修改 kernel 时改动更少（kernel 小） 两个用户级服务通信时，消息要在不同地址空间之间复制
更容易移植到新硬件
更安全可靠：kernel mode 运行的代码少；大多数服务是用户进程，一个服务崩了，OS 其余部分不受影响

例：Windows NT 是 layered microkernel，性能比 Windows 95 差；Windows XP 变得更 monolithic（把功能移进 kernel）。

往年考法：关于 microkernel 错误的是「通常性能比 monolithic kernel 好」（实际更差）。容易扩展、更容易移植、memory management 等服务可以放在用户空间——都对。

8.7 Loadable Kernel Modules（LKM，modular approach）

  • 当前最好的 OS 设计方法
  • kernel 有一组核心组件，可以在启动时或运行时通过 module 链接额外服务
  • 主要思想：kernel 提供核心服务，其他服务在 kernel 运行时动态实现和加入
  • 动态链接服务优于直接往 kernel 里加新功能——后者每次修改都要重新编译整个 kernel
  • 例：把 CPU scheduling 和 memory management 算法放在 kernel 里，通过 loadable modules 支持不同的文件系统

和 layered、microkernel 的比较：

  • 像 layered：每个 kernel section 有定义清楚、受保护的接口；但更灵活——任何 module 可以调用任何其他 module
  • 像 microkernel：主 module 只有核心功能和「怎么装入、怎么与其他 module 通信」的知识；但更高效——module 之间通信不需要 message passing

Linux 用 LKM，主要支持 device drivers 和 file systems。LKM 可以在启动时或运行时「插入」kernel，也能在运行时移除。例：插入 USB 设备，如果 kernel 没有对应 driver，可以动态装入。⇒ 动态、模块化的 kernel，同时保持 monolithic 的性能。

（Solaris 的模块化：core Solaris kernel 周围有 scheduling classes、file systems、loadable system calls、executable formats、STREAMS modules、miscellaneous modules、device and bus drivers 七类模块。）

8.8 Hybrid systems

  • 实践中很少 OS 只用一种严格定义的结构；它们组合不同结构 ⇒ hybrid systems，兼顾性能、安全、可用性
  • Linux：monolithic（单一地址空间，高效）+ modular（可动态加功能）
  • Windows：大体 monolithic，但保留一些 microkernel 的特征——支持作为用户态进程运行的独立子系统（personalities）；也支持动态装入的 kernel modules

8.9 结构对比总结（必背）

结构 做法 优点 缺点
Monolithic 所有功能在一个静态二进制、单一地址空间 效率高（system call 开销小、内部通信快） 难修改、难调试和维护
Layered 分层，底层硬件、顶层 UI，每层只用下层 构造和调试简单 性能差（穿多层）；层难定义
Microkernel 最小 kernel，多数服务是用户态程序，message passing 通信 易扩展、易移植、安全可靠 性能差（用户 / kernel 通信、消息复制）
LKM 核心 kernel + 运行时可装入 / 移除的 modules 灵活（任意 module 互调）、高效（不用 message passing）
Hybrid 组合（多为 monolithic + modules） 兼顾性能、安全、可用性

8.10 macOS、iOS 与 Darwin

  • macOS 和 iOS 架构上有很多共同之处：UI、编程语言支持、图形和媒体、kernel 环境——Darwin（含 Mach microkernel 和 BSD UNIX kernel）
  • Mac OS X 结构：hybrid、layered——Aqua UI（鼠标 / 触控板）→ application environments and services（Java、Cocoa（Objective-C API）、Quicktime、BSD）→ kernel environment（BSD、Mach、I/O kit、kernel extensions）
  • iOS：基于 Mac OS X 结构加了功能；不能原生运行 Mac OS X 应用；运行在不同 CPU 架构（ARM vs Intel）；Springboard UI（为触控设计）；Cocoa Touch（Objective-C API）；Media services（Quicktime、OpenGL）；Core services（云计算、数据库）；Core OS（基于 Mac OS X kernel）

Darwin：

  • layered 系统，由 Mach microkernel 和 BSD UNIX kernel 组成——hybrid 的 XNU kernel
  • 两套 system-call 接口：**Mach system calls（叫 traps）**和 BSD system calls（提供 POSIX 功能）
  • 接口是丰富的库：标准 C 库、网络、安全、编程语言支持
  • Mach 提供基本 OS 服务：内存管理、CPU scheduling、IPC
  • BSD 提供 POSIX API、网络、文件系统、安全
  • kernel 环境提供 I/O kit（device drivers）和动态装入的 modules，叫 kernel extensions（kexts）

8.11 Android

  • Open Handset Alliance（主要由 Google 领导）开发；开源、运行在多种移动平台（对比：iOS 只在 Apple 设备上，闭源）
  • 和 iOS 类似，是 layered 系统，有丰富的框架支持图形、音频、硬件功能
  • 不用标准 Java API，Google 设计了独立的 Android API；Java 应用运行在 Android RunTime（ART）上——为内存和 CPU 有限的移动设备优化的虚拟机
  • JNI（Java native interface）：让开发者绕过虚拟机，写能访问特定硬件功能的 Java 程序；用 JNI 写的程序通常不能跨硬件移植

Android 架构：

  • 库：web 浏览器框架（webkit）、数据库（SQLite）、网络（如 SSL）
  • HAL（hardware abstraction layer）：抽象所有硬件（相机、GPS、传感器），给应用提供与具体硬件无关的一致视图
  • Google 开发了 Bionic 标准 C 库（而不是 Linux 的 glibc）
  • 底层是修改过的 Linux kernel（为移动系统加了电源管理等）

9 · OS 简史

时代 特点
硬件贵、人便宜 手工编程机器（1945–1955）：硬件利用率低 → batch processing（1955–1965）→ multiprogramming（1965–1980）：内存中多个作业，复用 CPU
硬件便宜、人贵 Time sharing（用户用便宜终端共享服务器）→ personal computer（利用率不再是主要问题，重视 UI 和 API）→ distributed OS（一致性、性能、可靠性、资源管理）→ real-time OS（保证或优先处理作业）

11 · 易错点

  • Error detection：错误可能在 CPU、内存、I/O 设备、用户程序，不只是内存和 I/O。
  • printf() 是 library call，它调用 write() system call；调用 printf() 时还在 user mode。
  • API 不比 system call 快，也不能绕过 kernel 保护；优点是方便和可移植。
  • Block 和 stack 方法不限制参数个数和长度；registers 方法会受限。
  • Microkernel 性能比 monolithic 差（不是更好）。
  • Linux 是 monolithic + modular（hybrid），不是 microkernel。
  • Darwin 是 Mach microkernel + BSD，Mach 的 system call 叫 traps。
  • Policy 是「做什么」，mechanism 是「怎么做」；timer 是 mechanism。
  • LKM 比 microkernel 高效，因为 module 间通信不用 message passing。
